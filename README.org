* selfdidactic/switchyard
:PROPERTIES:
:CUSTOM_ID: selfdidacticswitchyard
:END:

Switchyard is a non-interactive Clojure CLI that loads a specification
document for processing. Specifications may use Markdown or Org format.

** Installation
:PROPERTIES:
:CUSTOM_ID: installation
:END:
Clone or download the project from
https://github.com/selfdidactic/switchyard and install Clojure CLI.

** Usage
:PROPERTIES:
:CUSTOM_ID: usage
:END:
Run the CLI from source:

#+begin_example
$ clojure -M:run-m --spec path/to/spec.md
{:spec "path/to/spec.md"}
#+end_example

The CLI resolves its configuration (see [[#configuration][Configuration]]) and prints the
resulting complete configuration in EDN. This version does not yet load or
act on the specification; use =--validate= to check that it can be read.
Specification files may be =.md=, =.markdown=, or =.org=; extensions are
matched case-insensitively.

Running without arguments uses the bundled =switchyard.toml=:

#+begin_example
$ clojure -M:run-m
{:spec "resources/sample-project/specification.md"}
#+end_example

If the configuration is missing a required key, running without arguments
prints help instead.

Build the uberjar:

#+begin_example
$ clojure -T:build ci
#+end_example

Then run the same CLI from the generated jar:

#+begin_example
$ java -jar target/net.clojars.selfdidactic/switchyard-0.1.0-SNAPSHOT.jar --spec path/to/spec.org
$ java -jar target/net.clojars.selfdidactic/switchyard-0.1.0-SNAPSHOT.jar --version
switchyard 0.1.0-SNAPSHOT
#+end_example

** Options
:PROPERTIES:
:CUSTOM_ID: options
:END:
#+begin_example
-h, --help         Show help for using the program
-v, --version      Show the program version
-s, --spec PATH    Path to a Markdown or Org specification document
-c, --config PATH  path to toml config file
    --validate     validate configuration and print it in edn format
#+end_example

Help takes precedence over every other option (even with an unreadable
=--config=). Version takes precedence over everything except help.

- =-c, --config PATH= reads the TOML file at PATH. When omitted, the
  =switchyard.toml= resource on the classpath is used (bundled in
  =resources/= and in the uberjar); a missing default resource is an empty
  configuration, but a missing explicit =-c= file is an error.
- =--validate= reads the effective specification path (from =--spec= or the
  config file) to confirm it exists, has a supported format, and is
  readable, then prints the configuration. Errors name the path and where it
  came from.

** Timetable
:PROPERTIES:
:CUSTOM_ID: timetable
:END:
A timetable describes what Switchyard runs: harnesses, agents, skills,
prompts, and pipelines. It is written as EDN maps in any number of files.
The files together form *one logical timetable*; file names and boundaries
carry no meaning. The example files in =resources/timetable= split it by
root key, but a single =switchyard.edn= works equally well, as does any
grouping (=common.edn=, =clojure.edn=, =development.edn=).

Load a directory with =selfdidactic.timetable/load-dir=: it reads every
=*.edn= file in sorted name order, merges them, and validates the result.

*** Merging
Fragments are merged recursively. When both values are maps they merge;
otherwise the later value replaces the earlier one. Vectors are replaced,
never concatenated, and a later =nil= replaces a map.

#+begin_example
;; base.edn                          ;; override.edn
{:agents                             {:agents
 {:reviewer                           {:reviewer
  {:harness :hermes                    {:model "~anthropic/claude-sonnet"}}}}
   :model "~deepseek/flash"
   :skills [:acd :review]}}}

;; merged
{:agents
 {:reviewer {:harness :hermes
             :model "~anthropic/claude-sonnet"
             :skills [:acd :review]}}}
#+end_example

Because load order decides conflicts, numeric prefixes make a handy
override convention: =00-base.edn=, =10-clojure.edn=, =90-local.edn=.

*** Validation
Only the merged timetable is validated (with clojure.spec); a single file
may hold any partial slice. The root keys are a closed set, so an unknown
key such as =:agent= is reported:

| Root         | Required | Contents                                          |
|--------------+----------+---------------------------------------------------|
| =:harnesses= | yes      | name → ={:command string ...}= (extra keys allowed) |
| =:agents=    | yes      | name → ={:harness kw :model string :skills [kw]}=   |
| =:prompts=   | yes      | name → ={:path string}=                             |
| =:pipelines= | yes      | name → ={:steps [{:agent kw ...} ...]}=, at least one step |
| =:skills=    | no       | name → ={:path string}=                             |

Validation is structural only: references between sections (an agent's
harness, a step's prompt) are not checked. A failure throws =ex-info= whose
data lists the =:problems=.

** Configuration
:PROPERTIES:
:CUSTOM_ID: configuration
:END:
The =selfdidactic.config= module loads a TOML file, converts it to an EDN
map, and reads it through [[https://github.com/yogthos/config][yogthos/config]]. Only keys from the TOML file are
used; environment variables and system properties do not affect values.
Command-line options override the file: =--spec= replaces =spec=.

=resources/switchyard.toml=:

#+begin_example
spec = "resources/sample-project/specification.md"
#+end_example

The spec path is a filesystem path relative to the working directory.

A configuration is /complete/ when it has every required key (currently
=spec=, supplied by =--spec= or =spec= in the config file). Behavior, first
matching row wins:

| Situation                                       | Result                                          |
|-------------------------------------------------+-------------------------------------------------|
| missing keys and =--validate=                   | error listing the keys and how to supply them, exit 1 |
| missing keys, no arguments                      | help, exit 0                                    |
| missing keys, other arguments                   | usage error listing the missing keys, exit 2    |
| complete and =--validate=                       | validate the spec, print the configuration, exit 0 |
| complete                                        | print the configuration in EDN, exit 0          |

** Exit codes
:PROPERTIES:
:CUSTOM_ID: exit-codes
:END:

- =0=: help, version, or the configuration was displayed.
- =1=: the config file is missing or invalid, required configuration is
  missing under =--validate=, or =--validate= could not load the
  specification (unsupported format, unavailable, or unreadable).
- =2=: the command line is invalid, such as an unknown option, missing option
  value, positional argument, repeated =--spec=, or missing required
  configuration when other arguments are given.

** Development
:PROPERTIES:
:CUSTOM_ID: development
:END:

Start a REPL in =selfdidactic.cli= (=selfdidactic.switchyard=
holds =-main=):

#+begin_example
$ clj -M:repl
selfdidactic.cli=>
#+end_example

Run the tests:

#+begin_example
$ clojure -T:build test
#+end_example

Run the complete CI task and rebuild the uberjar:

#+begin_example
$ clojure -T:build ci
#+end_example
